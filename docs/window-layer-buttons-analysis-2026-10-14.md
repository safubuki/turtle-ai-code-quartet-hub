# 最前面・最背面ボタンの修正

日時: 2026-10-14  
深刻度: Major（前後移動の主要操作が反映されない）  
状態: 修正済み。実IDE・複数ディスプレイでの目視確認は未実施。

## 現象と原因

標準表示の「最前面」「最背面」と縮小表示の「前」「背」は同じClickハンドラを使う。「最前面」は通常Z帯へ `HWND_TOP` で上げる補正だけだった。「最背面」は非フォーカス窓だけを背面へ送り、集中窓へ実行する `EnsureFocusedSlotAboveTiles` が無条件に前面化して背面指定を取り消していた。

修正前の2026-10-12ビルドを検証ツールへ読み込むと、「標準・4面の前面ボタンで全窓が管理外窓より前へ移動」の検証が失敗した。集中表示の背面指定を無視する経路はソースでも確認した。

## 修正内容

1. 明示的な前面ボタンは既存の `BringToFrontOnce` を使い、一時的なtopmost化の後に通常Z帯へ戻す。フォーカス遷移や自動補正の通常前面化は従来どおりにする。
2. 集中窓の順序補正は管理レイヤーを参照する。背面指定なら集中窓を末尾へ送り、その後に同面のタイルを末尾へ送って「他アプリ > 集中窓 > タイル」を保つ。共通処理なので再適用と遅延確定にも反映される。
3. 操作後はパネル本体を即時に前面へ戻す。非表示中は前後指定だけを更新する。
4. 明示的な前面操作直後の相対配置は、既存の遅延Z順検査へ回す。別スレッドの集中窓が一時topmost解除を処理する前にタイルを相対配置すると、そのタイルまでtopmostになる競合を別スレッド検証で確認した。集中窓が通常帯へ戻ってから違反したタイルだけを補正し、全ディスプレイの集中窓を検査する。

Win32の `HWND_BOTTOM` はtopmostを解除してZ順の末尾へ移し、`HWND_NOTOPMOST` は通常帯へ戻す指定である。[MicrosoftのSetWindowPos仕様](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)に沿い、既存の `SWP_NOACTIVATE` と `SWP_ASYNCWINDOWPOS` を維持する。

常時最前面固定、集中解除、位置・サイズ変更は追加しない。通常の最前面固定アプリより上へ居続ける操作にはしない。

## 検証

- 既存の回帰チェック74件が合格。
- 既存の直接最大化・復元・自動補正のWPF統合チェック12件も修正後の本体で合格。
- `tools/WindowLayerChecks` の統合24件が合格。実際のXAMLボタンのClickから、非表示の検証専用トップレベル窓のZ順を読み取る。同一スレッドと窓ごとの別スレッドで同じ12項目を確認し、非同期要求も対象にする。
- 標準・縮小の4面/集中表示での背面化と再前面化、集中の維持、通常Z帯への復帰、再適用、周期Z順補正、遅延確定、非表示中の保留を確認した。
- 非同期要求が未処理の一瞬を成功と扱わず、各検査で100msのDispatcher処理猶予を置いてからZ順とtopmostフラグを確認する。
- 検証用窓とパネルは表示せず、周期更新・保存・名前オーバーレイを抑止し、保存先を隔離する。ユーザーの外部IDEを操作しない。
- 本体と検証ツールのビルドは警告・エラー0。

## 実機の確認手順

1. 通常の他アプリを管理窓の上へ開き、標準表示の「最前面」で管理窓がその手前へ移ること。
2. 「最背面」で他アプリの後ろへ移り、集中表示中でもサイズ・フォーカス枠を保つこと。
3. 周期更新や遅延補正後も背面が維持され、続けて「最前面」で再び手前へ移ること。
4. 縮小表示の「前」「背」で同じ操作を確認する。複数ディスプレイに管理窓を分けても全対象へ適用されること。
